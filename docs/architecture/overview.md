# Current architecture and acceptance boundaries

The development workspace contains the game runtime, chat/PvP process stubs and an isolated protocol experiment. The runtime review branch includes only the game process and its required crates. `shared` owns process configuration, structured logging, liveness and shutdown. `amf-codec` owns bounded binary envelopes without HTTP or database dependencies. `game-server` owns gateway dispatch, persistent gameplay and asset delivery.

SQLx/MySQL persistence uses the exported original schema. Authentication verifies original password/session formats with explicit account/character ownership. Purchases, crafting, promotion and mission rewards use transactions; in-memory mission tokens serialize duplicate completion and expire after 30 minutes. Saved progress survives restart, while unfinished mission tokens do not. Chat/PvP ownership and transport integration remain future work.

Initial interfaces are intentionally narrow: `decode(bytes, Limits) -> Envelope`, `encode(Envelope, Limits) -> bytes`, `shared::run(service, port, Router)`. Explicit `Value::Amf3` represents embedded AMF3 data; the envelope version does not automatically wrap values. Reject unsupported values and bounded malformed input rather than silently coercing it.

The actual AIR client has verified accounts, village and first-mission battle/completion. Expanded progression has headless AMF/MySQL coverage. Additional AMF types, later actual-client flows and production realtime transport remain acceptance gaps. Development-only `socket-protocol` and `protocol-spike` verify legacy text polling in isolation; they are excluded from runtime review and deployment images. The user's revised priority is complete gameplay loops before lower-priority polish. See [progress](../migration/progress.md) and [production promotion policy](../branch-policy.md).
